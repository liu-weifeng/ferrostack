VM **online (live) migration** (`POST /api/vcenter/vm/{vm}/migrate {dest_host}` → `ferrovirt/src/service/vm_migrate.rs`) is implemented and the orchestration is sound — pre-flight checks: VM running, **all data disks on petrel shared storage** (vMotion-style: only RAM+device state migrate, disk stays on shared petrel), no cdrom media, dest≠src, memtier-shared-backing handling; flow = export → dest `-incoming` → `migrate tcp:` → flip `vm.host_id` → src cleanup, with rollback.

**BLOCKER on the lab (hardware, not software):** the two nodes are heterogeneous Haswell-EP — 123 = E5-2673 v3 @ 2.40 GHz, 106 = E5-2696 v3 @ 2.30 GHz — with **different TSC frequencies and no VMX TSC scaling**. So a 123↔106 live migration transfers RAM/state fine but the **dest QEMU refuses on load** (`TSC frequency mismatch … TSC scaling unavailable` + `kvm-tpr-opt load failed`) → migration fails at the finish + rolls back. No software can make this preserve guest timekeeping; needs matching CPUs or TSC-scaling hosts (Skylake+).

**Two compounding causes:** (1) `-cpu host` (host-passthrough) binds the guest CPUID/features to the source host → cross-host CPUID/feature mismatch; (2) TSC frequency mismatch (independent of CPU model).

**User's chosen direction (2026-06-16):** start VMs with a **compatible CPU model instead of host-passthrough** (vMotion-EVC style — a baseline model both hosts support, or the feature intersection). Added a TODO **「虚拟机 CPU 模式配置」** to xvirt `CLAUDE.md` 工作进展 (top entry): add `cpu_mode`/`cpu_model` to `vm_config` + create/edit API + front-end dropdown + agent/lictor emit `-cpu <model>` per config. NOTE: CPU-model normalization fixes CPUID/feature portability; the **TSC freq mismatch is a SEPARATE problem** — a compatible model + Linux-guest kvmclock MIGHT survive it (untested), but strict TSC-correctness still needs TSC-scaling HW. Optional companion: add a CPU/TSC pre-flight check to `vm_migrate.rs` to refuse incompatible migrations cleanly (instead of the current blind-attempt-then-dest-fail+rollback).

**vm_migrate.rs gap:** it does NOT pre-check CPU/TSC compatibility (only disks). Did NOT implement a fix this session — user redirected to the configurable-CPU-mode approach (TODO). The CLAUDE.md edit is uncommitted in the xvirt repo working tree.

## BREAKTHROUGH (2026-06-16): 123↔106 live migration SUCCEEDS — "TSC blocker" was a RED HERRING

Re-investigated against our own QEMU source (`/root/code/xvirt/qemu`, branch memory-tiering) and found the prior "TSC hardware blocker" conclusion was WRONG/contaminated. Three real issues, all fixed → **migration now completes**:

1. **TSC freq mismatch is NON-FATAL in our QEMU.** `target/i386/kvm/kvm.c:5314` explicitly: "TSC frequency mismatch shouldn't abort migration, unless the user explicitly asked … (e.g. tsc-freq option)". `kvm_arch_set_tsc_khz` only `warn_report`s (line 921), never aborts — we don't pin tsc-freq. So TSC was just a co-printed WARNING, not the cause. (Guest can still avoid TSC clocksource via kvm-clock; that's orthogonal and good practice, but isn't what blocked migration.)

2. **The actual fatal error was `kvm-tpr-opt load failed`** = the legacy **kvmvapic** device (`hw/i386/vapic.c`, vmstate name "kvm-tpr-opt"; `vapic_post_load`→`vapic_prepare` returns -1 on the dest). Unrelated to TSC. Disabled via **`-global kvm-apic.vapic=off`** (APIC prop `vapic` defaults true, `DEFINE_PROP_BIT` in `hw/intc/apic_common.c:413`; under KVM the apic type is `kvm-apic`). The kvmvapic device is created lazily only when the guest enables it (`apic_common.c:288`); with vapic=off it never exists → no "kvm-tpr-opt" vmstate to load. **Implemented**: lictor `support/qemu_command.py` `_build_machine` appends `-global kvm-apic.vapic=off` when env `XVIRT_DISABLE_VAPIC` ∈ {1,true,yes}. Deployed to 123+106 (`/usr/lib/python3/dist-packages/lictor/support/qemu_command.py`) + systemd drop-in `/etc/systemd/system/xvirt-lictor.service.d/vapic.conf` sets `Environment=XVIRT_DISABLE_VAPIC=1`, lictor restarted. **Change is in the lictor working tree, NOT committed.**

3. **THE REAL BLOCKER: QEMU version skew between nodes.** After vapic was fixed, dest failed with `Machine type received is 'pc-q35-10.0' and local is 'pc-q35-10.2' → load of migration failed: post load hook failed for: configuration`. Root cause: **106 was running STOCK Ubuntu QEMU `1:10.2.1+ds-1ubuntu3`** (its `qemu-system-x86` pkg = the actual `/usr/bin/qemu-system-x86_64`) while **123 runs our custom `qemu-kvm-xvirt-10.0.7+gitf11a9d3b9f`**. The stock pkg has **epoch `1:`** which always outranks our `10.0.7+git` (no epoch) → an `apt upgrade` had silently swapped 106's emulator to stock 10.2.1 (its `qemu-system-common`/`-gui` stayed custom 10.0.7 = a broken mixed install). Default machine `q35` → resolves to `pc-q35-10.0` on 123's QEMU, `pc-q35-10.2` on 106's → configuration vmstate mismatch. **Fixed**: copied `build-deb/out/qemu-*_10.0.7+gitf11a9d3b9f_*.deb` to 106, `dpkg -i --force-downgrade` (back to custom 10.0.7), then **`apt-mark hold`** all qemu pkgs so apt can't re-clobber. Verified `qemu-system-x86_64 --version` = 10.0.7 on both.

**RESULT: with (1) cpu_mode=custom Haswell-noTSX + (2) kvm-apic.vapic=off + (3) matched custom QEMU 10.0.7 on both nodes, a 123→106 live migration of a petrel-dist-disk VM COMPLETED**: task success, `vm.host` flipped to 106, dest `qemu:migtest4` alive on 106 with **CLEAN stderr (no TSC error, no kvm-tpr-opt, no machine-type mismatch)**, source QEMU cleanly gone from 123. So the earlier "needs TSC-scaling HW / Skylake+" conclusion was wrong — these heterogeneous Haswell-EP nodes CAN live-migrate once the QEMU builds match and the legacy vapic device is off.

**Follow-ups (not yet done):** (a) commit the lictor qemu_command.py vapic change + decide default-on vs per-VM config vs keep env-gated (currently needs `XVIRT_DISABLE_VAPIC=1` in lictor's env on every node); (b) **packaging: the custom qemu deb needs an epoch (or pin/hold baked in)** so `apt upgrade` never swaps in stock Ubuntu qemu — this hit 106 and will hit any node; also `apt-mark hold` qemu on 123 (only 106 held this session); (c) minor: after migration `vm.state` stays NULL in DB on the new host (reconcile/event gap — should write `running`); (d) `/usr/libexec/qemu-kvm` symlink was manual on 106 — bake into xvirt-init/qemu deb. Lab cleaned up (migtest VMs deleted, count 0).

This is the full real-guest confirmation on top of the earlier empty-guest migtest4 — the vapic-off + same-qemu-version + custom-CPU fixes make heterogeneous Haswell-EP 123↔106 live migration actually work end to end.

**Gotchas hit getting a guest booting on petrel (record for next time):**
- **petrel disk vol name is SYSTEM-DERIVED** `<vm_uuid>-<disk_uuid>`, NOT the `vol` field you pass at create (that's ignored). To preload an image you must write to that derived name.
- **pool matters**: petrel-dist datastore → petrel **pool 3**. `petrel-ublk serve --vol <name>` WITHOUT `--pool 3` looks in the default pool, doesn't find the VM's vol, and silently CREATES a 512MB stray. Must serve `--vol <derived> --pool 3 --vol-size <bytes>` to open the real one.
- **petrel-ublk write-back cache flush**: after `qemu-img convert` + `sync`, WAIT ~12s before stopping the serve, else the gateway cache hasn't flushed to OSD → the VM's separate vhost gateway reads incomplete data → SeaBIOS "not a bootable disk". (Matches the documented "sleep 8s after write" note.)
- preload recipe: `petrel-ublk serve --vol <derived> --pool 3 --vol-size 8589934592 --mon <ip>:6790` → `qemu-img convert -S 0 -O raw -t none img.qcow2 /dev/ublkbN` → sync + sleep 12 → pkill serve.
- **images**: `/root/ubuntu-bench/golden.qcow2` is UEFI-only (no BIOS GRUB → SeaBIOS won't boot it). `/var/lib/xvirt-test/base.qcow2` is Debian 12, BIOS-bootable (it runs a leftover `membench` that OOM-spams the console, harmless). Static IP injected via `/etc/systemd/network/10-static.network` ([Match] Name=e*); needed `modprobe nbd max_part=16` first (nbd wasn't loaded).
- **NIC**: pass `source_dev:"br-ex"` explicitly in the create interface — `resolve_source_dev` short-circuits on it, avoiding the network-handle→backend resolution that earlier produced `ovs-vsctl add-port 2`.

**Ubuntu-port BUG surfaced (not blocking migration, but UEFI VMs need it):** ferrovirt's OVMF path constants (`vm_create.rs:27-30`) point to the **Rocky/RHEL** path `/usr/share/edk2/ovmf/OVMF_CODE.fd`, but Ubuntu installs OVMF at `/usr/share/OVMF/OVMF_CODE_4M.fd`. Added compat symlinks on 123+106 (`/usr/share/edk2/ovmf/OVMF_CODE.fd → /usr/share/OVMF/OVMF_CODE_4M.fd` etc.) so OVMF/TianoCore loads. Proper fix: change the ferrovirt constants to the Ubuntu `*_4M.fd` paths (or have xvirt-init/packaging create the symlinks). Note also: base.qcow2 / Ubuntu cloud images that are UEFI-only need an ESP fallback `/EFI/BOOT/BOOTX64.EFI` or an NVRAM boot entry to auto-boot under fresh OVMF.
