The "replica=2 seqread 回归" on the lab cluster (123+106) had causes uncovered in stages. My "OSD mixed-R/W collapse / consumer-HDD-fundamental" diagnosis was **itself later overturned** — see the UPDATE at the bottom: the residual collapse was mostly the **unbounded gateway cache**, fixed by MR!6, after which replica=2 seqread recovered 0.8→**78 MiB/s**.

**1. PRIMARY — gateway dirty-extent cache panic (the real bug, FIXED).** `petrel-client` `CachingObjectAccess` (the dirty-extent rewrite, MR!3 commit 6077998) had a flush/overlay **race**: `flush()` does `mem::take(&mut e.dirty)` then **releases the lock** for async backend writes; a concurrent `read_object` overlay rebuilds `e.data` from the (shorter) backend object + now-empty dirty → **`e.data` shrinks**, losing in-flight bytes; the async write then **fails** (OSD RPC timeout) → flush's error path re-`merge_range`s the dirty extent, now **out of bounds** vs the shrunk `e.data` → next flush slices `e.data[oob]` → **panic in a locked section → poisons the mutex → whole gateway dies → seqread hangs forever (disk idle)**. The "seqread崩到1-17MiB/s" I'd seen was this crash, not disk contention.
Fix (MR!3, commit **ec23711**, pushed): `read_object` overlay **never shrinks `e.data`**, preserves ALL local `valid` bytes (incl in-flight), backend only fills holes; flush slice clamped defensively (never panic under lock). Regression test `caching_flush_overlay_race_no_poison` (blocking+fail-injecting backend reproduces the exact interleave) — **fails-before / passes-after** (verified). Validated: fixed gateway → 0 panics, seqread completes (baseline hung forever).

**2. RESIDUAL collapse is consumer-WD-HDD-FUNDAMENTAL, not flush-tunable.** petrel data OSDs are on consumer WD HDDs (`osd.0 data_bdev=/dev/sda device_class=hdd`; meta/WAL on NVMe). 实测 coalesce build: replica=2 pool seqread **0.8 MiB/s** vs replica=1 pool seqread **51.9 MiB/s** (clean). Cause: replica=2 → each OSD is BOTH primary (serves reads) AND replica (flushes the other node's replicated deferred backlog) → during seqread the HDD does concurrent random read + deferred-flush write → consumer-HDD R/W thrash → collapse. **No flush-layer change fixes this.** Real fix = faster write-path drain so backlog clears before reads (group-commit/pipelined replication, see [[petrel-writepath-perf]]) or put data on SSD/NVMe.

**Read-aware flush PACING was the WRONG lever (abandoned).** Implemented OSD-side "pace deferred flush when reads active", but it made seqread WORSE — because bluestore `read()` **overlays all unflushed deferred for the object**, so delaying flush → reads carry growing overlay cost → reads slower → more pacing → vicious cycle. For read perf you want deferred flushed PROMPTLY, not paced. Reverted entirely.

**What shipped instead — deferred COALESCING (MR!4, branch perf-deferred-coalesce, commit 2637b1a).** `Allocator::alloc_contig(n)` + `materialize_object` packs an object's touched 64KiB blocks into a **physically-contiguous run, one sequential write** (was n scattered random writes); falls back to per-block when no contig run. Net positive: replica=2 randwrite **911→1169 IOPS (+28%)**, sequential layout helps reads too, no replica=1 regression. Does NOT fix the HDD-fundamental replica-2 seqread collapse (orthogonal).

**Lab deploy state:** both 123+106 OSDs run the coalesce build (`/usr/local/bin/petrel-osd` size 10789640, matches MR!4). Gateways (`petrel-ublk`/`petrel-vhost` in /usr/local/bin) run **main** = NO dirty-extent cache → no panic risk (MR!3 unmerged). The fixed dirty-extent gateway only lives in `/root/petrel-ublk-fix` on 123 for testing.

**OSD redeploy procedure (works, used repeatedly):** must `pkill -9 -f "petrel-osd demo"` BEFORE `cp` new binary (else "Text file busy"); the pkill drops the SSH session with `exit 255` (BENIGN — reconnect and continue); then `cp /root/<bin> /usr/local/bin/petrel-osd` + `systemctl restart xvirt-hyper-agent` (reconcile restarts the 5 OSDs from the new binary; KillMode=process spares them on plain restart, so you MUST kill them explicitly to reload). Wait for `petrel-mon usage --mon 192.168.2.123:6790` → 10/10 + 慢请求=0. `slow=N` sticky flag = benign consumer-HDD recovery latency. Bench harness `/root/ublk-ab.sh <ublk-bin> <pool> <label>` (pool 2=replica2, pool 4=replica1); fio at `/root/fio` + `LD_LIBRARY_PATH=/root/fiolibs`.

## UPDATE (write-path group-commit/流水线复制 session, same lab): residual collapse was the UNBOUNDED GATEWAY CACHE, not consumer HDD

Did pipelined replication + found the real seqread-collapse cause. Two more MRs (open, not merged):

**MR!5 `perf-pipelined-replica-commit` (petrel-pg, commit 89656d9): 副本写 off-worker 提交.** Replica-side `PgCommand::Replicate` ran `handle_replica_op` INLINE in the shard worker → each RepOp blocked on its own group-commit fsync → replica group-commit batch always 1 (primary already had async_commit; replica didn't → replication pushed write tput to ~1/3 not 1/2). Fix: `prepare_replica_write` (in-worker: build txn + optimistic last_version/log/trim) + spawn the commit via spawn_blocking, chained per-PG via `fanout_tail` → cross-PG replica commits batch in group-commit. Order safe (same-PG serialized by primary's per-op ack-wait + fanout_tail); client ack still waits replica on_commit. Test `async_commit_replica_path_concurrent_writes_consistent`.

**MR!6 `fix-gateway-cache-oom` (petrel-client, commit on branch): 网关缓存内存按 max_bytes 兜底 — THE big win.** Gateway (petrel-ublk) got **oom-killed (RSS 10GB)** under replica=2 large-volume sustained randwrite. Root cause: sparse HIGH-OFFSET small writes → `write_object` `data.resize(end,0)` inflates each object buffer to ~whole-object size (zero-pad), but the inline-flush trigger used `dirty_bytes()` = sum of dirty *extent* lengths (4k/write) → undercounts real RSS ~1000× → backpressure never fires; `evict()` only drops CLEAN objects (all just-written = dirty) → unbounded dirty RAM → OOM. Fix: trigger inline flush on `dirty>max_dirty` **OR `c.bytes(total RSS)>max_bytes`** → flush().await (backpressures writer) turns dirty→clean → evict bounds RSS to max_bytes. Test `cache_memory_bounded_under_sparse_high_offset_writes` (200 sparse writes: 200MB→bounded; fail-before/pass-after).

**SURPRISE side effect = the actual seqread fix.** With the bounded gateway cache + backpressure, the randwrite no longer buffers a giant un-flushed backlog that then dumps during the following seqread. Final bench (piperepl OSD + OOM-fixed gateway, clean cluster):
- replica=2 (pool-2): seqW 87 MiB/s, randW **678 IOPS** (HONEST durable rate — the prior 909-1170 was un-sustainable buffering that led to OOM), **seqR 78.6 MiB/s** (was 0.8-1.8 — collapse GONE).
- replica=1 (pool-4): seqW 145, randW 1782 IOPS, seqR 73.9 MiB/s.
So the replica=2 "consumer-HDD-fundamental seqread collapse" conclusion was WRONG — it was the unbounded gateway cache. randwrite is "lower" now only because it's the real sustainable durable throughput (no OOM-bound buffering).

**MERGED + DEPLOYED (final).** MR!5 (`77d08e8`) + MR!6 (`4fb2056`) merged to main. Rebuilt petrel-osd + petrel-ublk + petrel-vhost from main and deployed to **`/usr/local/bin` on both 123+106** (OSD via kill→mv→hyper-agent restart; ublk/vhost via atomic `mv` — `cp` over a running binary gives ETXTBSY, `mv`/rename is safe; backups `.bak-premain`/`.bak-preoomfix`). Deployed-stack smoke (using `/usr/local/bin/petrel-ublk`, replica=2): seqW 84.5, randW 1200 IOPS, **seqR 79.1 MiB/s, RSS 3GB (no OOM)** — confirmed. OOM-killed process was always the gateway, never an OSD (OSDs survived every restart).

**Packaged + deb-deployed (final final).** Built `xvirt-petrel` deb from main: `ONLY=xvirt-petrel SKIP_RUST=1 ./build-deb-xvirt/build-xvirt-debs.sh` → `build-deb-xvirt/out/xvirt-petrel_0.0.1+git4cf8e0c_amd64.deb` (5 CLIs into /usr/local/bin; version label = **xvirt-repo** HEAD, not petrel HEAD). `dpkg -i` on 123+106 → both now `ii xvirt-petrel 0.0.1+git4cf8e0c`; running OSD exe = `/usr/local/bin/petrel-osd` owned by the deb (`dpkg -S` confirms). NOTE: petrel deb postinst now **auto-reloads** (was `exit 0`): on `configure`, if `xvirt-hyper-agent` is active it does `pkill -9 -f "petrel-osd demo"` + `systemctl restart xvirt-hyper-agent` → reconcile re-spawns OSDs from the new binary (gateways ublk/vhost auto-pick-up next spawn). ## Read-path parallel + readahead (MR!7, branch perf-read-path-parallel-readahead, NOT merged)

User asked to make the read path parallel + add readahead. Cold sequential read was capped ~80 MiB/s (~7% of raw nvme1n1 1091). Three changes:
1. **petrel-pg: OSD parallel reads** (the real fix). Replicated reads ran INLINE in the shard worker (`handle_read`→sync `store.read`) → serialized per shard + blocked the async runtime thread (EC reads already spawned off). Now: in-worker PG-state/coll lookup, then `spawn_blocking(store.read)`. Reads are side-effect-free → safe to parallelize.
2. **petrel-client: single-flight** on cache misses (per-oid async lock) → concurrent sub-object reads to the same uncached object fetch the whole object once, not N×.
3. **petrel-client+ublk: sequential readahead** — `Volume::prefetch_hint` (bounded A:Clone+Send+Sync+'static) background-prefetches next `PETREL_READAHEAD_WINDOW` objects (env, default 16, 0=off); ublk read handler calls it.

**KEY measurement lesson:** the standard ublk-ab seqread (right after randwrite) is NOISE-dominated — randwrite's draining OSD deferred backlog + gateway write-cache make seqread swing 78↔213 regardless of readahead. Must use a CLEAN cold-read A/B (seqwrite → kill+restart serve for fresh cache → drain → cold seqread; script `/root/ra-clean.sh` on 123) to measure read honestly. Clean results (replica=2 nvme tier):
- readahead alone (OSD reads still inline): 80→81 (NO help — OSD read serving was the cap).
- **OSD parallel reads + readahead window=32: 80→113 MiB/s (+40%)**. window=0 stays 81 (parallelism only pays off when readahead supplies concurrent requests).
Remaining gap (113 vs 1091 raw) = single-queue ublk `block_on` demand path + OSD read overhead → next lever is **multi-queue ublk gateway** (parallelize the demand path), not more readahead. vhost path didn't get prefetch wired yet (would need a method on the AsyncBlock trait).

Lab: both 123+106 OSDs run the parallel-read build (`/root/petrel-osd-pread`); test gateway `/root/petrel-ublk-ra2` (readahead, env window). MR!7 open. **User switched to ENGLISH for logs/commit messages from here on** (fixed the xvirt-petrel postinst echo to English too).

## Multi-queue ublk investigation → the read cap is the 1 GbE NETWORK, not the gateway (no rewrite done)

User asked to make the ublk gateway multi-queue to parallelize the demand path. Investigation findings (NOT what was expected):
- ublk gateway is **already multi-queue**: `petrel-ublk serve --queues` defaults to **4** (4 queue threads). But each queue serializes (`run_queue`→`handle_io`→`block_on`, 1 IO at a time per thread); a single fio job hits one hw queue → ~1× concurrency.
- Queue-scaling test (clean cold read, queues=jobs=4/8/16): **181 / 215 / 182 MiB/s — plateaus ~200**, does NOT scale with queue count. Cap is DOWNSTREAM of the gateway queues.
- **Root cap = single 1 GbE NIC** (`/sys/class/net/enp7s0/speed=1000`; iperf-equivalent python TCP test 123→106 confirmed **941 Mb/s = 112.2 MiB/s delivered = saturated 1GbE**; one NIC for mgmt+cluster+storage on 192.168.2.0/24, ~118 MiB/s/direction usable). replica=2 reads: ~half served by the remote primary osd.9@106 over 1GbE; writes: every replica copy crosses it. So cold read ~180-215 = local-disk-fast half + 1GbE-capped remote half. raw nvme1n1=1091 but the network is 1GbE → the ~9× read gap to raw is largely the NETWORK.
- **Conclusion: did NOT implement async-per-queue / more queues** — the data shows it can't exceed the 1GbE link (futile + risky IO-path rewrite, like the vhost async saga). The real levers are NETWORK: 10/25GbE NIC, a dedicated storage network, or NIC bonding. Software read parallelism is already adequate for the link (4-8 queues reach the cap; single-stream readers would only benefit up to the same 1GbE cap).
- Per-queue async (single-stream 106→~200) is the only remaining software gain and is bounded by 1GbE → not worth the rewrite risk on this hardware.
Lab unchanged (no new binary deployed for this; OSDs still on the MR!7 parallel-read build `/root/petrel-osd-pread` = current main). Test scripts on 123: /root/ra-clean.sh, /root/q-scale.sh, /root/mq-test.sh.

**NIC bonding NOT possible:** each node has exactly ONE physical 1GbE NIC (123 enp7s0 / 106 enp6s0, both r8169) — bonding needs >=2 NICs. Confirmed link already at line rate (941 Mb/s). Only real network levers = add a 2nd NIC (then bond, ~2x for petrel's 16-conn mux multi-flow) or 10GbE. Jumbo frames (MTU 9000) would add only ~1-2% (already 94% of line rate). Did NOT reconfigure the single NIC's br-ex (pure risk, no benefit).

## Real-VM E2E test (vhost-user-blk) found + fixed a guest-write-EIO bug (committed dbef622 → main)

User asked to confirm E2E IO with a real VM. Harness: /root/ubuntu-bench/ (Ubuntu 24.04 cloud img golden.qcow2 + bench.service→/usr/local/bin/bench.sh auto-runs fio on the petrel vol), launcher /root/petrel-ubuntu-bench.sh <vol> <size> <pool> <mon> <label> <tmo>; petrel vol attached via vhost-user-blk (petrel-vhost serve --socket). VM boots over vhost → petrel-vhost → mux → OSD.
- **Confirmed E2E works**: Ubuntu VM boots fully, 4GiB petrel vol visible as /dev/vda, IO runs, clean poweroff.
- **Found a real bug**: sustained guest writes hit a fatal I/O error (`I/O error dev vda ... WRITE` at sector ~1068168 ≈ 547MB into a 1G write). Root cause: OOM-fix backpressure did `flush().await?` and flush() fanned out ALL dirty extents in one join_all → 256MB dirty trigger bursts ~256 concurrent 1MB RPCs over the saturated 1GbE → some hit the 15s RPC timeout → that transient flush error propagated as a FATAL guest write error (data was already cached!).
- **Fix (dbef622, main)**: flush() bounds fan-out to PETREL_FLUSH_FANOUT (default 32, chunked) → no burst; write_object backpressure made best-effort (`let _ = flush().await`) so a transient flush hiccup doesn't EIO the cached write (failed extents re-merged to dirty + retried), with a hard 2×-max_bytes guard preserving OOM protection. Test backpressure_flush_failure_is_best_effort_then_2x_guard. Post-fix: NO guest I/O error, VM runs progressively longer (more IO completing) + clean poweroff.
- **In-guest fio MiB/s NOT cleanly extractable** from the golden harness: bench.sh's fio echoes don't surface on serial (systemd ordering / output quirk) and nbd re-inject of a file-writing bench.sh loses writes (lazy-umount + forced qemu-nbd disconnect doesn't flush). Not a petrel issue. Throughput is network-bound = the ublk-measured numbers (cold read ~80-200 MiB/s, randwrite ~1200 IOPS replica=2). For future clean VM numbers: forward SSH (hostfwd) into the guest + run fio directly, or fix the nbd-inject to use a non-lazy synced umount before disconnect.
- Deployed: both 123+106 /usr/local/bin petrel-vhost=7955856 + petrel-ublk=8931976 (committed main dbef622). Test scripts on 123: /root/petrel-ubuntu-bench.sh, /root/myboot.sh; golden /root/ubuntu-bench/golden.qcow2.
