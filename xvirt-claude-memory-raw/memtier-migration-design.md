Big QEMU-fork feature (user-requested 2026-06-06), branch `memory-tiering`. Four parts:

1. **Raw-disk backing (local + petrel vol)** — ALREADY works in QEMU core: `memtier/memtier.c:tier_init` opens `path` `O_RDWR|O_DIRECT`, handles `S_ISBLK`+`BLKGETSIZE64`. So `/dev/nvme1n1` or `/dev/ublkbN` (petrel vol via `petrel-ublk` serve) work as backing today. Work = orchestration only (create vol, serve ublk, set memtier.json `path`).
2. **Create petrel volume** — orchestration (hyper-agent `support/petrel/volume.py` + `petrel-ublk create/serve`).
3. **Migration: skip swapped pages + dest reuse shared volume + auto-enable** — ZERO integration today (`grep memtier migration/` = 0; current flow must `x-memtier-disable` first = faults everything back).
4. **Heat-aware first round** — resident=hot (send), swapped=cold (skip; on shared volume).

**Locked design (user-confirmed):**
- Backing = **distributed petrel volume** (cross-host shared); both src+dst `petrel-ublk` serve the SAME vol (local /dev/ublkbN may differ → serialize the petrel *volume name*, not raw path; dst resolves to its local ublk).
- "Skip swapped pages" is a **migration capability** `memtier-shared-backing` (negotiated on BOTH ends — dst must also be set up to reuse vol). Default OFF = today's safe behavior. Orchestrator turns ON for src+dst only when the distributed vol is reachable on dst (QEMU can't know this itself — user's point).
- Mechanism mirrors QEMU's **`ramblock_dirty_bitmap_clear_discarded_pages`** (virtio-mem): at migration setup, clear migration dirty bits for SWAPPED pages → never sent. Quiesce eviction during migration (no new RESIDENT→SWAPPED). Faulted-in pages during migration: memtier swap-in marks them dirty (`memory_region_set_dirty`) so they're sent (slot freed). meta[] (gfn→state+slot) serialized via a **savevm handler** ("memtier", runs stop-copy after RAM). Dst: open shared vol, restore meta, MADV_DONTNEED swapped pages + re-arm uffd MISSING, receive only resident pages over wire, auto-enable.

**Hard constraint:** memtier (anon RAM + uffd) ⊥ vhost-user-blk (shared memfd). So a memtier VM's petrel *disk* must use petrel-ublk (/dev/ublkbN as plain -drive), NOT vhost-user. (The migration vMotion work earlier used vhost-user for the DISK; memtier path is different.)

**Key QEMU files:** `memtier/{memtier,worker,fault,scan,slot-alloc}.c` + `memtier-int.h`; `qapi/memtier.json` (x-memtier-* QMP, `path` already = raw dev); `qapi/migration.json` (add capability); `migration/ram.c` (`ramblock_dirty_bitmap_clear_discarded_pages` precedent @~853, `migration_bitmap_clear_dirty` @794); `migration/savevm.c:register_savevm_live`; `memtier/memtier-stubs.c` (non-linux). No public memtier header yet — create `include/system/memtier.h`.

**Stage B — DONE** (ferrovirt `5f975dc` + hyper-agent `e07fa98` + lictor `b3b0857`; deployed center 121 + 106, lictor migration.py also on 123). ferrovirt `vm_migrate.rs` detects memtier VM (vm_config.memtier_enabled) → dest `memtier_backing_setup(vol=mtswap-<uuid>, size=current_memory_bytes)` before -incoming → `memtier_shared:true` to migrate_incoming/out → src `memtier_backing_teardown` on success (keep shared vol), dest teardown on any failure. **Convention:** vol name `mtswap-<vm_uuid>`, symlink `/var/lib/xvirt/memtier/<uuid>.swap`. **VM-start distributed backing — DONE** (hyper-agent `3e1ad20`, lictor `3ef0cdc`): `_write_memtier_sidecar` defaults tiered VMs to distributed petrel backing when a petrel cluster is present (backing_kind=petrel, backing_vol=mtswap-<uuid>, path=symlink, no file; falls back to raw file w/o petrel). lictor `_memtier_enable_on_start` serves the vol (memtier_backing.setup) before x-memtier-enable; `_cleanup_petrel_vhost_for_vm` tears down ublk serve + symlink on stop (keeps vol). Verified live on 123: memtier config w/o path → petrel sidecar. **page-idle-broken-on-106 FIXED 2026-06-07** (qemu `d4075ce153`): adaptive uffd-WP write-aging. Root cause: page_idle never reflects EPT accesses for guest RAM on 106/123 (E5-26xx v3) → cold scan always ncold=0 → eviction stuck at 0 (memtier non-functional there; works on dev host 114). Fix: worker counts consecutive evict-allowed-but-nothing-evicted windows; after 30 flips region to `writeage_fallback` (one-way) → `scan_range_cold` marks every PRESENT page (pagemap PFN works where page_idle doesn't) a candidate; eviction WP-rollback + cooldown-on-abort (fault_tick set in evict_complete_one) = write-hotness filter. Read-hotness unmeasurable on these CPUs → read-hot churn (cooldown-bounded); but write-heat is the right signal for migration anyway. Verified: 106 auto-flips, swaps 167MB (was 0); 114 stays on page_idle (no flip/regression). **Design impact:** on E5-26xx v3 hosts memtier heat = write-heat (no read-hotness); the migration first-round "send cold only" optimisation still works (cares about re-dirty=writes). Env-gated trace `XVIRT_MEMTIER_TRACE` kept.

**Confirmed migration design (user, 2026-06-07):** dirty bitmap = always-on baseline (保底) every round; first round optimised by memtier's OWN heat (send cold only, defer hot to later rounds/cutover — heat comes from memtier when tiering is on, no separate DAMON needed); subsequent rounds pure dirty bitmap; memtier-shared-backing layer additionally skips already-swapped pages (on shared file/LUN). NOTE: the fork's existing `migrate_hotness_aware()` does the OPPOSITE (full round-1, filter later rounds, own monitor not memtier) — needs rework to "round-1 = memtier-heat cold-only + later rounds pure dirty bitmap" if/when feature 4 is wired. memtier Stage A already keeps the dirty bitmap as baseline (clears only swapped bits at round-1 setup, re-dirties faulted-in pages).

**Cross-host E2E 106→123 — 2026-06-07, headline verified, dest-finalize hard-blocked by TSC (not memtier):** with memtier now functional on 106 (write-aging), ran a real cross-host migration: distributed petrel vol `mtswap-<uuid>` served as ublk on BOTH hosts (same vol, same per-VM symlink); src write-aging drained **161MB** to that distributed vol; migration **completed** on src and **SKIPPED exactly the swapped pages: skipped=39424 == swapped=39424** (cold pages NOT sent over the wire, cross-host). ✅ headline. The DEST then **failed device-state load**: `error loading 'kvm-tpr-opt'` + `TSC frequency mismatch (VM 2294686 vs host 2394455 kHz), TSC scaling unavailable` → `load failed: Operation not permitted`. Pinning a fixed `tsc-frequency` doesn't help — Haswell-EP (E5-26xx v3) has **no VMX TSC scaling**, and 106(2.29GHz)↔123(2.40GHz) have **no common native TSC**, so a guest can't run at a non-native TSC → **cross-host live migration 106↔123 is hard-blocked for ANY VM** (same reason the earlier ordinary vMotion left the dest unstable; pre-existing env limitation, NOT memtier). The dest-restore + cold-page-readback path is the SAME code already PROVEN on localhost (ref==dst md5). So the memtier cross-host feature is verified to the extent the hardware allows; full dest-readback needs CPU-homogeneous / TSC-scaling-capable (Skylake+) hosts. Test harness fully cleaned; center VM intact.

**⚠ CROSS-HOST E2E BLOCKED — root-caused 2026-06-07 to PETREL-UBLK (not memtier/QEMU):** memtier eviction **STALLS at ~80 pages** when backing is a **DISTRIBUTED** petrel-ublk device (`petrel-ublk serve --mon` → remote OSDs). Decisive isolation:
  - memtier + **mem-backed** ublk (`petrel-ublk serve --backend mem`) on 114: **FULL SUCCESS** — evicted 39725 pages + swapin 2048 faults, **0 errors**. So memtier-on-ublk + memtier io_uring O_DIRECT + uffd+KVM all work.
  - memtier + **local file** backing: full success (localhost migration PASS).
  - memtier + **distributed** petrel-ublk on 106: eviction climbs to **evicted=80 then frozen** (swapped=80 pages), QMP stays responsive, **no crash**, serve process **alive** w/ clean log, swapin_errors=0. The high-QD (EVICT_QD=256, 512KB runs) concurrent io_uring O_DIRECT **writes stop completing** — the distributed petrel-ublk write-completion path stalls under that load (plain single `dd` O_DIRECT to it works; it's the concurrency/burst that stalls).
  - (Earlier "crash/QEMU died" reports were a fragile test-harness QMP client mis-skipping async events, NOT a real crash — corrected.)
  - **VERIFIED 2026-06-07 (user asked "is it migration-specific?"): NO — memtier EVICTION itself is broken on node 106, not just migration/paused-test.** Re-tested with a RUNNING (not paused) guest + plain file backing on 106: eviction still frozen (evicted=57, swapped=0). scan diag trace: of 245760 pages only **present=32726** (~13%, the touched set; rest are untouched/demand-zero so legitimately skipped) and those present pages **all read back as accessed → cold=0** → nothing to evict. This is **host/CPU-specific**: page-idle idle-tracking (scan.c: /proc/self/pagemap PFN + /sys/kernel/mm/page_idle/bitmap, must be EPT-mmu-notifier-aware) is **not effective under KVM on 106 (Xeon E5-2696 v3)** — the idle bit never sticks for EPT-mapped guest RAM, so every present page looks hot. On the **dev host 114** the identical scan finds cold pages (evicted 39725; prior 104GB oversub also on 114). So **memtier as a whole only works where page-idle EPT tracking works (114), NOT on 106/123 (E5-26xx v3)**. ⇒ deployment caveat + a real memtier eviction bug to fix (scan.c idle-tracking robustness on these CPUs; or fall back to uffd-WP-only / DAMON when page_idle is ineffective).
  - **ORDINARY (non-memtier) live migration is UNAFFECTED on 106**: it uses KVM dirty-logging (KVM_GET_DIRTY_LOG / write-protect / PML = D-bit path), a DIFFERENT mechanism from page-idle (A-bit) — and the earlier vMotion of migtest 106↔123 succeeded. So the page-idle problem does NOT implicate ordinary migration.

Added env-gated trace (`XVIRT_MEMTIER_TRACE`, qemu `2681fb9585`). Trace at the stall shows: VM genuinely paused (`query-status`=paused/running=false), memtier worker looping healthily (`allow=1 can_scan=1 resident=262062 floor=8192`), but **`scan ... ncold=0` every pass** → nothing to evict → frozen at 80 (the very first scan caught 80 cold, then all pages report "accessed").   - **(earlier characterizations, superseded by the conclusive trace finding above):** it is **NOT petrel-ublk** — during the stall the petrel-ublk serve is fully **idle/healthy** (all 4 ublk queue threads in io_cqring_wait = no pending IO; tokio workers parked; clean log). It's a **memtier-side stall exposed by the distributed backing's higher write-completion latency** (mem-backed ublk AND local-file backings are low-latency and work perfectly — mem-ublk evicted 39725 + swapin 2048/0-err). At the stall (evicted frozen ~80): memtier worker thread is in `clock_nanosleep` (backoff, NOT evicting), memtier fault thread idle in `poll(uffd)`, and crucially **a vCPU thread is BLOCKED in `ioctl KVM_RUN` (fd=kvm-vcpu:0, cmd=0xae80, utime=0)** despite the VM being `stop`'d. ⇒ a vCPU faulted on a memtier-managed page (WP'd-for-eviction or DONTNEED'd/SWAPPED) and is blocked waiting for a uffd resolution that doesn't come; with a slow backing the eviction-write / swapin-read window is wide enough to expose a race/stall in the memtier uffd↔KVM↔io_uring fault/evict interaction.
