# Kestrel：推送式轻量监控框架设计

> 版本 v1.2，2026-11-19。名字 kestrel 为暂名。
> 代码在 `ferrostack/kestrel`（独立子仓）。本文 § 编号是代码注释里 `§x.y` 的指向。
> 状态：v1.2 把存储布局从「每对象一个环形文件」改成「多个对象共用的顺序追加文件」（第 5 章），已合进 main。
> 在测试机上编译通过，49 个测试、端到端脚本、1 万对象规模测试都跑过，新旧布局的实测对比见 §12.1。

## 0. 结论先行

- **推而不拉**：底层服务（hyper-agent、lictor、petrel、fulmar、cdp、qemu 等）在自己进程里取数，
  通过一条长连接把数据推给 `kestreld`。没有 exporter，没有 scrape，没有服务发现。
- **数据模型是「对象 + 指标集」**，不是「序列 + 标签」。一个监控对象（一台 VM、一块盘、一个 OSD）
  绑定一个指标集（一组有名字、有类型的字段），每次推送是一行。对象随时注册、随时离开。
- **存储是多个对象共用的顺序追加文件**，分 5 层分辨率（原始 / 1 分钟 / 5 分钟 / 1 小时 / 1 天），按时间窗口切分。
  精简在写入时增量完成；每个窗口到期后封存一次（按对象排序重写），过了保留期整个删掉，**没有持续的后台压实**。
- **突发保留有三道**：每个聚合桶都带 min / max / 峰值时刻；在线检测到突发时把那一段**原始分辨率
  的整行数据**另存为片段，按重要度长期保留；状态变化和突发都记成事件。
- **资源**：单线程 epoll，只依赖 libc。每个在线对象约 13 KB 内存（1 万对象实测 126 MB）；16 个字段的对象活满 2 年占
  约 2.6 MB 磁盘，且到此封顶。

与 Prometheus 类方案的差别：

| | Prometheus / VictoriaMetrics + exporter | Kestrel |
|---|---|---|
| 取数方向 | 上层按周期拉 | 底层主动推 |
| 采集进程 | 每类数据一个 exporter | 无，服务自己推 |
| 对象增减 | 服务发现 + 重新抓取 | 一帧注册，一帧注销，超时自动判失联 |
| 数据组织 | 每条序列一组标签，倒排索引 | 对象 × 字段，无标签索引 |
| 精简 | 后台压实，降采样另配 | 写入时增量聚合；过期窗口整个删掉；每份数据只重写一次 |
| 长期容量 | 随保留期线性增长 | 每层保留期固定，每对象封顶 |
| 突发 | 降采样后只剩平均值（或另存原始） | 桶内 min/max/峰值时刻 + 原始片段 |
| 查询 | PromQL | 按对象、字段、时间段直接读（§9） |

Kestrel 不做的事：PromQL、任意标签维度的即席聚合、告警规则引擎（§11 列为后续）。

## 1. 目标与约束

| 需求 | 对应设计 |
|---|---|
| 底层主动推送，不用 exporter | §3 推送协议，§10 SDK |
| 监控对象动态增减 | §2.1 对象生命周期，§4 注册表 |
| 多种监控项 | §2.2 瞬时值 / 累计量 / 状态 / 事件 |
| 随时间自动精简 | §5 分层环 |
| 保留关键突发波动 | §6 |
| 高效读取 | §5.4 每个窗口一次索引查找加一次读 |
| 高效精简管理 | §5.3 写入时聚合；过期是删整个窗口文件；每份数据只重写一次 |
| 资源占用低 | §8，实测见 §12.1 |

规模假设（用来估容量，不是硬上限）：1 万个对象，平均 16 个字段，10 秒一推，即每秒 1.6 万个值。

## 2. 数据模型

### 2.1 监控对象

对象由 **键** 唯一标识，形如 `类别/名字`：`vm/3f2a…`、`host/node1`、`osd/node1/3`、`disk/node1/nvme0n1`。
第一个 `/` 之前是类别。

每个对象有：

- **指标集**（§2.2），注册时声明，之后不变。
- **推送间隔**（秒，最小 1），注册时声明，之后不变。原始点的时间按这个间隔对齐。
- **属性**：若干 `k=v`，可以更新（VM 迁移后 `host` 变了，新主机上的 agent 重新注册即可）。
  属性只用于筛选和展示，不参与存储寻址，所以改属性不会让数据断开。
- **失联时限**：默认是推送间隔的 3 倍，最少 30 秒。

生命周期：

```
            注册                超过失联时限没数据            失联满 retire_after（默认 1 天）
  （无） ─────────► 在线 ──────────────────────► 失联 ───────────────────────────► 已退役
                     ▲                            │                                  │
                     └────────── 又来数据 ────────┘        退役满 purge_after（默认 30 天）
                     │                                                               ▼
                     └──── 显式注销（GONE 帧）────────────────────────────────►   删除文件
```

- 进入失联时记一条事件。这就是推送模式下的「死活检测」，替代拉模式里的 `up` 指标。
  服务端刚启动的 `startup_grace`（默认 120 秒）内不判失联，给底层留出重连的时间。
- 失联的对象释放内存，文件保留；再来数据时自动加载回来。
- 已退役的对象仍然能按 id 查历史，键改名为 `原键#id`，原键可以被新对象重新使用。
- 用同一个键注册、但指标集或间隔变了：旧对象立即退役，新建一个。历史不丢，只是分成两段。

### 2.2 指标集与字段类型

指标集是一个有名字的字段列表，最多 64 个字段。字段有名字、类型、单位、突发下限（§6.2）。

| 类型 | 推什么 | 服务端存什么 | 精简后保留 |
|---|---|---|---|
| 瞬时值 gauge | 当前值（f64） | 原值 | 每桶：和、个数、最小、最大、最大值出现的时刻 |
| 累计量 counter | 单调递增的累计值（u64） | 相邻两次之间的**每秒速率** | 同上（针对速率）；`和 × 间隔` 即桶内增量 |
| 状态 state | 小整数（u32） | 原值 | 每桶：出现过哪些状态（位图，0–63）、最后状态、变化次数；每次变化另记一条事件 |
| 事件 event | 时间、级别、代码、文本 | 事件日志（§7） | 按天整文件过期 |

- 累计量回绕或重置（新值小于旧值）时，按「从 0 重新开始」算增量。
- 服务端重启后每个累计量字段的第一个点没有速率（缺一个点），因为上一次的累计值只在内存里。
- 某次推送可以缺字段（行里带一个存在位图），缺的字段那个点为空。
- 分布类数据（延迟直方图）本版没有专门类型，用若干个累计量字段表示各个桶。

为什么一行一行推，而不是一条序列一条序列推：同一对象的各字段本来就是同一时刻取的，
合成一行后时间戳、对象标识只出现一次，服务端一次定位就写完整行，也不需要任何标签索引。

## 3. 推送协议

### 3.1 连接

底层服务与 `kestreld` 之间一条 TCP 长连接（默认端口 7410），由底层发起。一个进程一条连接，
一条连接上可以注册任意多个对象。选 TCP 不选 UDP：需要确认与重传（§3.4），而且指标集只声明一次，
之后的数据行里不带任何名字。

### 3.2 帧格式

所有整数小端。

```
u32 长度（类型 + 载荷的字节数，上限 1 MiB）
u8  类型
载荷
```

字符串是 `u16 长度 + UTF-8`。

底层 → 服务端：

| 类型 | 名字 | 载荷 |
|---|---|---|
| 0x01 | HELLO | u32 魔数 `KSTL`，u16 协议版本，str 来源（服务名），str 主机名，u64 会话号，str 口令 |
| 0x02 | SCHEMA | u16 指标集编号，str 名字，u16 字段数，每字段：str 名字，u8 类型，u8 标志，str 单位，f64 突发下限 |
| 0x03 | OBJECT | u32 对象编号，u16 指标集编号，str 键，u32 间隔秒，u32 失联时限秒（0 = 默认），u16 属性数，每属性：str k，str v |
| 0x04 | DATA | u64 序号，u16 行数，每行：u32 对象编号，i64 时间戳毫秒，u64 存在位图，每个存在的字段 8 字节 |
| 0x05 | EVENT | u64 序号，u32 对象编号（全 1 = 不属于任何对象），i64 时间戳毫秒，u8 级别，str 代码，str 文本 |
| 0x06 | GONE | u32 对象编号 |
| 0x07 | PING | u64 随机数 |

服务端 → 底层：

| 类型 | 名字 | 载荷 |
|---|---|---|
| 0x81 | WELCOME | u16 协议版本，i64 服务端时间毫秒，u64 该会话已落盘的最大序号 |
| 0x84 | ACK | u64 序号：不大于它的 DATA / EVENT 都已落盘 |
| 0x87 | PONG | u64 随机数 |
| 0x8E | ERROR | u16 错误码，u32 相关编号，str 说明 |

- 指标集编号、对象编号都是**连接内**的短编号，由底层自己分配，重连后重新声明。
- 字段值 8 字节：瞬时值是 f64 的位，累计量和状态是 u64。
- 类型 0（瞬时值）、1（累计量）、2（状态）。标志位 0 = 不做突发检测。
- 级别：0 信息，1 警告，2 错误，3 严重。

### 3.3 时间戳

时间戳由底层打，服务端把它**四舍五入**到对象间隔的整数倍，作为这个点的时间。SDK 默认按间隔对齐
取当前时间，所以正负半个间隔以内的抖动不会造成一个时刻两点或漏点。

服务端拒收的行（计数，回 ERROR，不断连接）：

- 时间不比该对象已有的最新点更新（重复或乱序）。重传的数据靠这条去重。
- 时间超前当前时间 `max_skew`（默认 120 秒）以上，或者早于原始层的保留范围。

各主机需要对时。WELCOME 里带服务端时间，SDK 可以据此发现偏差。

### 3.4 确认、重传与落盘

服务端**不写预写日志**。可靠性靠「落盘后才确认 + 底层缓冲未确认的数据」：

1. 底层给每个 DATA / EVENT 帧一个递增序号，发出后留在本地缓冲里。
2. 服务端收到后先放内存，每 `flush_interval`（默认 120 秒）把所有脏对象写进文件，
   对数据目录做一次 `syncfs`，然后给每条连接回 ACK。
3. 底层收到 ACK 后丢掉对应缓冲。
4. 连接断了就退避重连，重新声明指标集和对象，把没确认的帧原样重发。服务端按时间戳去重。

这样服务端重启、网络中断、服务端崩溃用的是同一套恢复办法，服务端少一份日志写入。
代价：

- 底层要留 `flush_interval` 加上同步时间、再加中断时长的数据。缓冲有上限（默认 4 MiB，按每行 `20 + 8 × 字段数` 字节算，
  10 秒一推时够约 1500 个 16 字段的对象；一个进程推得更多就要调大），满了丢最旧的并计数。
- 数据从推出到被确认要等最多一个 `flush_interval` 加一次 `syncfs`。查询不受影响：查询前会把该对象内存里的数据写进文件。
- 底层进程和服务端同时掉电，会丢最多一个 `flush_interval` 的数据。
- 服务端崩溃后重传的事件可能重复一次（会话的已收序号只在内存里）。

`syncfs` 在单独的线程里做，不挡收数。

### 3.5 口令与网络

本版只在 HELLO 里带一个预共享口令（配置了才校验），不加密。默认假定走管理网。

## 4. 注册表

`<数据目录>/registry.log`：追加写的记录（对象的完整元数据，或一条删除），启动时读完后重写一遍压缩。
只在对象新建、属性变化、状态变化时追加，推数据不碰它。

内存里两张表：键 → id，id → 元数据。id 是递增的 u64，也是文件名。

## 5. 时序存储

v1.0–v1.1 是每对象一个定长环形文件、原地写。规模实测（§12.1）发现它写放大大、脏页分散，
v1.2 起改成下面的布局：**多个对象共用、按时间窗口切分的顺序追加文件**。

### 5.1 层、窗口、日志与段

`<数据目录>/seg/` 下每层一个目录。每层的时间轴按固定长度切成**窗口**，一个窗口一组文件：

| 层 | 目录 | 一行是什么 | 保留 | 窗口长度 |
|---|---|---|---|---|
| 原始 | `raw` | 一个原始点 | `raw_span`，默认 2 小时 | `raw_span / 8`，默认 15 分钟 |
| 1 分钟 | `a60` | 一个聚合桶 | 1440 桶 = 1 天 | `seg_rows`（默认 32）个桶 = 32 分钟 |
| 5 分钟 | `a300` | 同上 | 2016 桶 = 7 天 | 160 分钟 |
| 1 小时 | `a3600` | 同上 | 2160 桶 = 90 天 | 32 小时 |
| 1 天 | `a86400` | 同上 | 730 桶 = 2 年 | 32 天 |
| 快照 | `open` | 一个对象各层未关闭的桶（§5.5） | 两个窗口 | `flush_interval × (partial_every + 2)` |

聚合层可配置，步长必须是上一层的整数倍，天按 UTC 对齐。对象只用步长大于自己推送间隔的聚合层。

一个窗口的数据有两种形态：

- **日志** `<窗口起点>-<窗口长>.<代号>.log`：追加写。每次落盘，每个有新数据的对象往里追加一个**块**：

  ```
  u32 魔数 | u32 行区长度 | u32 校验 | u32 行长 | u64 对象 id | 行 … | 补齐到 8 字节
  ```

  块在文件里的位置记在内存索引里（对象 → 块列表，每块 8 字节）。服务端启动时把现有日志顺序扫一遍重建索引，
  校验不过的残缺尾巴截掉。
- **段** `<窗口起点>-<窗口长>.seg`：只读。窗口结束并过了等待期（`max_skew + 2 × flush_interval`）之后**封存**一次：
  把日志按对象排序重写，每个对象的行连成一串，文件尾部是按对象 id 排序的索引（每项：id、偏移、长度、行长、校验）。
  封存后日志删掉，内存索引释放。

迟到的数据落到已经封存的窗口时，再开一个新代号的日志；下次维护把它和原来的段合并重写一次。
同一个对象同一时间有多行时，以后写的为准。

**行格式**（行本身不带校验，块和段各自带）：

```
原始行：u32 时间 | u32 保留 | 字段数 × f64                    （空值用 NaN）
聚合行：u32 桶起点 | u32 保留 | u32 桶内最后一个点的时间 | u32 保留 | 字段数 × 24 字节单元
```

24 字节单元：

```
数值字段：f64 和 | f32 最小 | f32 最大 | u32 个数 | u32 最大值相对桶起点的秒数
状态字段：u64 出现过的状态位图 | u32 最后状态 | u32 变化次数 | u32 个数 | u32 保留
```

最小、最大用 f32（约 7 位有效数字），和用 f64，所以平均值与累计量的积分是精确的，包络线略有舍入。

### 5.2 容量

每对象每秒产生的字节数（F 个字段，间隔 I 秒）：原始层 `(8 + 8F) / I`，每个聚合层 `(16 + 24F) / 步长`。
保留期满后的存量与旧布局相同：

```
(raw_span / I) × (8 + 8F) + Σ各聚合层桶数 × (16 + 24F)
```

F = 16、I = 10 秒、默认分层：原始层 98 KB，聚合层 6346 桶 × 400 B = 2.5 MB，合计约 **2.6 MB**，活满 2 年后不再增长。
另有每块 24 字节的块头，以及每层至多多留一个窗口。空间随数据增长，不预分配；对象不单独占文件，
所以注册、注销一个对象不产生任何文件操作。

### 5.3 写入与精简

每个在线对象在内存里有：待写的原始行、每个聚合层一个**正在累积的桶**、已经关闭但还没写的桶。

收到一行时：

1. 把时间对齐到间隔，去重，把累计量换成速率。
2. 对每个聚合层：这一行落在的桶如果不是当前桶，就把当前桶关闭（进待写队列），开新桶；
   然后把这一行的每个字段并进桶里（和、个数、最小、最大、峰值时刻）。
3. 行进待写队列。

每个值的代价是几次比较和加法，不读盘。**精简就是这第 2 步**，是写入时顺手做的。

落盘（每 `flush_interval` 一次）：每个有新数据的对象，把待写的原始行作为一个块追加到原始层当前窗口的日志，
把已关闭的桶追加到各聚合层的日志；每 `partial_every` 次（默认 10 次，即 20 分钟）再往快照层追加一行快照。
全部是往少数几个文件的末尾顺序写，新数据多少字节就写多少字节（加块头）。顺序固定：先原始层，后聚合层。

维护（每 5 秒看一次，每层每次最多做一个窗口）：

- **删过期**：窗口结束超过本层保留期的，整个文件删掉。老分辨率的数据就是这样消失的，没有逐条删除。
- **封存**：见 §5.1。这是每份数据唯一的一次重写，所以总写入量约为新数据的 2 倍，且都是顺序写。

`flush_interval` 仍是写盘批量与确认延迟之间的旋钮，但不再决定写放大。

### 5.4 读取

查某对象某些字段在 `[from, to]` 的数据：

1. 选层：覆盖得到 `from` 的层里，步长不大于 `(to - from) / 期望点数` 的最粗一层，
   这样返回的点数不少于期望值；没有这样的层就用覆盖得到的最细一层。也可以直接指定层。
2. 对与 `[from, to]` 交叠的每个窗口：有段，就在段尾索引里二分找到这个对象，一次读出它在这个窗口里的整串行；
   有日志，就按内存索引把它的各个块读出来。
3. 合在一起按时间排序，同一时间留后写的。

对象在线时，查询前先把它待写的行追加进日志的写缓冲（读得到缓冲里的块）；聚合层正在累积的那个桶直接从内存里补上。

代价：已封存的部分每个窗口一次二分加一次读。默认窗口下，1 分钟层查一天是 45 个窗口，5 分钟层查 7 天是 63 个，
1 小时层查 90 天是 68 个。未封存的窗口每个对象最多十几到三十几个块。比旧布局的「一到两次顺序读」多，
换来的是写入全部顺序化。`seg_rows` 调大则窗口少、读得快，但未封存窗口变大、内存索引变多。

原始层返回值；聚合层每个点返回平均、最小、最大、个数、峰值时刻。界面用最小最大画包络带，
任何缩放级别下尖峰都看得见。

### 5.5 崩溃恢复

持久化的东西只有三样：原始层的行、聚合层**已关闭**的桶、快照。正在累积的桶平时只在内存里，
靠下面两条能恢复出来：

- **快照**：每 `partial_every` 次落盘，把对象各层正在累积的桶打成一行写进快照层
  （行里「桶内最后一个点的时间」记着它累积到哪了）。快照层只留最近两个窗口。
- **用原始行重做**：原始层留着最近 2 小时的每一个点。

对象加载（注册时，或失联后又来数据时）：

1. 找到原始层里它最新的一行，时间记为 L。之后只收比 L 新的点。
2. 读出 `(L - W, L]` 的原始行，W = `flush_interval × (partial_every + 2)`，默认 24 分钟。
3. 对每个聚合层、窗口里涉及的每个桶：取它在本层里的行和快照里的行中累积得更靠后的那个（都没有就从空开始），
   把时间晚于「桶内最后一个点的时间」的原始行补进去。已经过去的桶有变化就写回本层；当前桶留在内存里接着累积。

因为先写原始层后写聚合层，原始层永远不比聚合层旧，这个重做是幂等的，崩在落盘中间的任何位置都能补齐。
W 保证了任何落后的桶都在窗口里。对象卸载和服务正常关停时，正在累积的桶直接作为本层的行写出去。

封存的崩溃安全：新段写好并改名后，被它取代的日志**不立即删**，等下一次 `syncfs` 成功后才删。
这之间崩溃的话段和日志都在，启动后两者再合并一次，结果相同；段里校验不过的部分被忽略，以日志为准。

## 6. 突发保留

精简以后还能看到突发，靠三样东西，从粗到细：

### 6.1 桶内包络（一直都有）

每个聚合桶带最小、最大、最大值出现的时刻。即使退到 1 天一个点，也知道那天的峰值是多少、几点出现的。
成本已经算在 24 字节单元里。

### 6.2 突发片段（原始分辨率，长期保留）

**检测**（每个数值字段一个检测器，在线，每个点常数时间）：

- 维护指数加权的均值 m 和平均绝对偏差 d（窗口默认 60 个点）。
- 偏离分 `z = |x − m| / max(d, 2% × |m|)`；`|x − m|` 小于字段的突发下限时偏离分记 0。
- 攒够半个窗口的点之后，`z ≥ k`（默认 8）即触发。
- 突发期间基线只按 1/8 的速度更新，免得基线被突发带走。

字段的**突发下限**是注册指标集时给的绝对值，意思是「变化小于这个数不算突发」。
比如 CPU 百分比给 10，一条长期为 0 的序列跳到 0.5 就不会触发。不给就只按相对量判断。

**成段**（按对象，不按字段）：任何一个字段触发，对象就进入突发态；连续 `quiet` 个点（默认 6）
所有字段的偏离分都低于 k/2 就结束；最长 `max_len` 个点（默认 360）强制结束，
此时认为是水平变化而不是突发，把触发字段的基线重置到当前值。

结束时把 `[触发前 pre 个点, 结束]`（pre 默认 12）这一段的**原始整行**从原始层抄出来，
存成一个片段。抄整行而不是只抄触发字段：排查时要看的正是同一时刻别的指标在干什么。
同时记一条事件，写明触发字段、峰值分、峰值时刻。

**保留**：片段存在 `<id>.burst`，追加写。文件超过上限（默认每对象 256 KB，16 字段时约 60 个片段）
或有片段超过 `burst_keep`（默认 365 天）时重写一次：丢掉过期的，剩下的按
`重要度 = 峰值分 × 0.5^(年龄 / 30 天)` 从高到低保留到上限的 3/4。
所以越剧烈的突发留得越久，普通的小波动先被挤掉。

### 6.3 事件

状态字段每次变化、每个突发片段、对象失联与恢复，都进事件日志（§7）。
底层服务自己知道的关键时刻（迁移开始、后端盘写满）也用 EVENT 帧推上来。

## 7. 事件日志

`<数据目录>/events/ev-<UTC 日序号>.log`，按天一个文件，追加写，随落盘一起刷。
查询按时间段扫对应的那几天的文件，可以按对象筛。过期（默认 90 天）就是删整个文件。

## 8. 服务端结构与资源

```
        底层服务（SDK）                                  界面 / 脚本
             │ TCP 7410，推送协议                            │ HTTP 7411，JSON
             ▼                                               ▼
   ┌──────────────────────────── kestreld（单线程 epoll）────────────────────────────┐
   │  接入：拆帧、连接内编号 → 对象 id                 查询：解析请求、拼 JSON        │
   │                         ┌──────────── Store ────────────┐                        │
   │                         │ 注册表  在线对象  事件日志     │                        │
   │                         │ 聚合桶  突发检测  片段文件     │                        │
   │                         └───────────────────────────────┘                        │
   │  定时：每 5 秒查失联与过期；每 flush_interval 落盘                               │
   └──────────────────────────────────────┬───────────────────────────────────────────┘
                                          │ 请求 / 完成通知（eventfd）
                                   同步线程：syncfs
```

- 一个线程处理收数、查询、定时，Store 不加锁。每秒 1.6 万个值离单核上限差几个量级。
  查询读文件会短暂挡住收数，由 TCP 缓冲吸收。
- 打开的文件只有各层未封存窗口的日志（通常每层一两个）；对象不单独占文件，所以对象数不受文件描述符上限限制。
- 依赖只有 libc。HTTP 解析、JSON 输出、配置解析都是手写的最小实现。
- 内存：每个在线对象 = 各层累积桶 `4 × (16 + 24F)` + 检测器与累计量状态 `40F` + 最近一行 `8F`
  + 待写行。F = 16 时约 3 KB，加上待写数据、表项和未封存窗口的块索引，实测每对象约 13 KB，1 万对象 126 MB（§12.1）。
  失联对象只剩块索引那一小部分。
- 自身运行数据在 `/api/v1/stats`。

## 9. 查询接口

HTTP GET，返回 JSON。时间参数是秒；`from`、`to` 为负数时表示相对当前时间。

| 路径 | 参数 | 返回 |
|---|---|---|
| `/api/v1/objects` | `class` `state` `prefix` `attr.<k>=<v>`，可选 `schema=1`、`limit` | 对象列表：id、键、状态、属性、指标集名、间隔、最近一次数据时间；`schema=1` 时带字段列表 |
| `/api/v1/latest` | `class`、`field`，可选 `attr.<k>`、`limit`、`order=desc\|asc` | 各在线对象该字段的最新值，从内存出，不读盘。用于总览和排行 |
| `/api/v1/series` | `key` 或 `id`，`fields=a,b`（缺省全部），`from` `to` `points`（默认 600），可选 `tier` | 所选层、步长、时间数组、每字段的值（原始层）或 平均/最小/最大/个数/峰值时刻（聚合层） |
| `/api/v1/bursts` | `key` 或 `id`，`from` `to`，可选 `data=0` 只要摘要 | 突发片段：起止、触发字段、峰值分、峰值时刻、原始行 |
| `/api/v1/events` | `from` `to`，可选 `key` / `id`、`limit` | 事件列表 |
| `/api/v1/stats` | | 服务端自身计数 |

跨对象的聚合（某主机上所有 VM 的 CPU 之和的历史曲线）本版不在服务端做：由知道归属关系的
底层服务把它作为另一个对象推上来（hyper-agent 推 `host/<名>`），或由调用方取多条后自己加。

## 10. SDK

三种语言，行为一致：后台维持连接，断线退避重连并重新声明，缓冲未确认的帧，按间隔对齐时间戳。

| 语言 | 位置 | 给谁用 | 线程 |
|---|---|---|---|
| Rust | `crates/kestrel-client` | petrel、fulmar、cdplog、ferrovirt | 一个后台线程 |
| Python | `sdk/python/kestrel.py`（单文件，只用标准库） | hyper-agent、lictor | 一个后台线程 |
| C | `sdk/c/kestrel.{h,c}` | qemu、concilium、cdp | 无线程，调用方定期调 `kst_poll` |

用法都是四步：连接 → 声明指标集 → 注册对象 → 周期推一行。例（Python）：

```python
c = kestrel.Client("10.0.0.9:7410", source="hyper-agent")
vm_schema = c.schema("vm.basic", [
    kestrel.gauge("cpu_pct", "%", floor=10),
    kestrel.gauge("mem_used", "B"),
    kestrel.counter("disk_wr_bytes", "B"),
    kestrel.state("power"),
])
vm = c.object("vm/" + uuid, vm_schema, interval=10, attrs={"host": hostname, "name": name})
vm.push([cpu, mem, wr_bytes, 1])        # 每 10 秒
vm.event(kestrel.WARN, "migrate", "to node2")
vm.gone()                               # VM 删除时
```

## 11. 本版不做、后续可做

| 项 | 说明 |
|---|---|
| 告警 | 推模式下数据到达即可在内存里判阈值，不需要另一个轮询器。本版只有事件 |
| 跨对象聚合查询 | 见 §9 |
| 直方图类型 | 见 §2.2 |
| 传输加密、按来源授权 | 见 §3.5 |

## 12. 实现状态与验证步骤

代码布局：

| 目录 | 内容 |
|---|---|
| `crates/kestrel-proto` | 帧编解码、指标集类型 |
| `crates/kestrel-store` | 文件布局、聚合单元、检测器、片段、事件日志、注册表、Store |
| `crates/kestrel-client` | Rust SDK，`examples/hostpush.rs` 推本机 CPU / 内存 / 负载 |
| `bins/kestreld` | 服务端：epoll 循环、接入、HTTP 查询、配置 |
| `sdk/python`、`sdk/c` | Python、C SDK |

2026-11-19 在 10.8.1.195 上做了第 1–4 步（第 2–4 步固化成了 `tests/e2e.sh`），全部通过；
第 5 步（规模）的结果见 §12.1，脚本是 `tests/scale.sh`。Python、C 两个 SDK 只过了语法 / 编译，没有对着服务端跑过。步骤：

1. `cargo build --release && cargo test`（单测覆盖帧编解码、寻址与环绕、聚合、检测器、
   片段读写与重写、推入 → 查询、重启恢复）。
2. `kestreld --data /var/lib/kestrel`，另一终端 `cargo run --example hostpush -- 127.0.0.1:7410`，
   `curl 'http://127.0.0.1:7411/api/v1/objects'`、`…/series?key=host/<名>&from=-600`。
3. 杀掉 `kestreld` 再起，确认 hostpush 自动重连、数据不断、聚合层没有重复计数。
4. 给 hostpush 的主机加一段负载，确认 `/api/v1/bursts` 里出现片段。
5. 规模：用 hostpush 的 `--objects N` 模拟 1 万对象，看内存、CPU、落盘量是否与 §5.2、§8 的估计相符。

### 12.1 规模实测（2026-11-19）

10.8.1.195，数据目录在一块机械盘（XFS）上，`tests/scale.sh`：1 万对象 × 16 字段 × 10 秒间隔。
三轮，每轮只跑了一次，没有在 SSD / NVMe 上测过：

- A：旧布局（每对象一个环形文件），30 秒落盘，12 分钟。
- B：旧布局，120 秒落盘，25 分钟。
- C：新布局（§5，共用的顺序追加文件），120 秒落盘，45 分钟，期间封存了 4 个窗口。

| 项 | A 旧布局 30 秒 | B 旧布局 120 秒 | C 新布局 120 秒 |
|---|---|---|---|
| 吞吐（每秒值数） | 16178 | 15969 | 16025 |
| 拒收的行 / IO 错误 | 0 / 0 | 0 / 0 | 0 / 0 |
| 内存（RSS） | 95 MB | 111 MB | 126 MB（每对象 13 KB） |
| CPU | 0.79% 单核 | 0.59% | 0.59% |
| 进程写入 | 2.8 MB/s | 1.1 MB/s | 0.39 MB/s |
| 设备写入（含文件系统日志） | 3.1 MB/s | 1.3 MB/s | 0.41 MB/s（每天约 35 GB） |
| 相对新数据（约 200 KB/s）的倍数 | 约 14 倍 | 约 5 倍 | 约 2 倍 |
| `syncfs` 一次 | 4.5–52 秒 | 6.7–43 秒 | 0.3–1.5 秒 |
| 落盘时主循环停顿 | 125–250 ms | 240–330 ms | 120–180 ms |
| 维护（含封存）时主循环最长停顿 | — | — | 684 ms |
| 注册 1 万对象 | 1.0 秒 | 1.2 秒 | 0.6 秒 |
| `kill -9` 后全部加载回来 | 2.2 秒 | 2.8 秒 | 9.1 秒 |
| 重启后数据缺口 | 无 | 无 | 无 |
| 单对象原始层 10 分钟 | 0.7–1.5 ms | 0.8–1.7 ms | 0.9–1.7 ms |
| 1 万对象取最新值排行 | 6.7 ms | 6.3 ms | 6.7 ms |
| 列出全部对象（2.5 MB） | 44.5 ms | 42.2 ms | 42.0 ms |

C 轮 45 分钟共追加 593 MB、封存重写 404 MB；结束时段存储占 659 MB，其中原始层 378 MB、1 分钟层 203 MB、
5 分钟层 102 MB、快照层 32 MB。

结论：

1. **写入量和同步耗时的问题解决了。** 写入量是旧布局同样落盘周期下的三分之一强，而且全部是顺序写，
   机械盘上 `syncfs` 从几秒到几十秒降到 1.5 秒以内。
2. **代价一：重启恢复变慢**，2.8 秒 → 9.1 秒。启动时要把未封存的日志顺序扫一遍重建索引，对象加载时还要读快照和原始行。
   仍在 `startup_grace`（120 秒）以内。
3. **代价二：内存多了约 15 MB**（未封存窗口的块索引），每对象 13 KB，高于最初 8 KB 的估计。
4. **封存在主循环里同步做**，1 万对象时最长一次停了 0.68 秒，期间收数由 TCP 缓冲吸收。对象数再多一个量级要挪到后台线程。

没测到的：

- 长时间范围的查询。C 轮只跑了 45 分钟，「1 分钟层查 1 天」实际只读到 2 个窗口（1.0 ms），
  不代表 §5.4 说的读 45 个窗口时的耗时，尤其是页缓存没命中的时候。
- 数据活满各层保留期之后的稳定状态（窗口过期删除、5 分钟层及以上的封存）。
- 模拟负载里每个对象每 5 分钟变一次状态，1 万对象 45 分钟产生了 9.5 万条事件；真实服务的状态字段不该这么频繁地变。
